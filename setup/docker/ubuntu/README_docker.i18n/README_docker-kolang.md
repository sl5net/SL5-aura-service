docker run -it --rm --name stt-container stt-service

docker exec stt-container touch /tmp/sl5_record.trigger


Docker를 사용하여 애플리케이션을 컨테이너화하는 것은 환상적인 "멋진" 단계입니다. 이는 애플리케이션과 모든 종속성을 하나의 이식 가능한 이미지로 패키징하여 "내 컴퓨터에서 작동" 문제를 해결하는 궁극적인 방법입니다.

그러나 이 애플리케이션은 호스트의 데스크톱(오디오, 키보드)과 상호 작용하도록 설계되었기 때문에 몇 가지 근본적인 문제에 직면하게 됩니다. 이는 Docker가 *방지*하기 위해 명시적으로 설계된 것입니다.

### Docker 이미지를 빌드하고 실행하는 방법

1. **이미지 빌드:** 프로젝트 루트에서 터미널을 열고 다음을 실행합니다.
    ```bash
    docker build -t stt-service .
    ```
2. **컨테이너 실행:**
    ```bash
    docker run -it --rm --name stt-container stt-service
    ```

### 결과: 작동하는 것과 (비판적으로) 작동하지 않는 것

운이 좋다면 컨테이너가 빌드되고 실행될 것입니다. 시작되어 모델을 로드했으며 현재 대기 중임을 나타내는 `aura_engine.py`의 로그 출력이 표시되어야 합니다.

**이것은 부분적인 성공입니다!** 핵심 Python 애플리케이션과 해당 종속성은 완벽하게 격리된 환경에서 실행됩니다.

**그러나 이제 Docker의 설계로 인해 애플리케이션이 근본적으로 손상되었습니다.**

1. **마이크 액세스 불가:** 컨테이너는 호스트 하드웨어에서 격리됩니다. `sounddevice` 라이브러리가 입력 장치를 찾으려고 하면 실패합니다.
* *해결 방법(Linux에만 해당):* `docker run` 명령에 `--device /dev/snd`를 추가하여 호스트의 사운드 장치를 컨테이너에 마운트해 볼 수 있습니다. 이는 복잡하고 호스트별로 다릅니다.

2. **입력 출력 없음(`xdotool`):** 컨테이너는 호스트의 데스크톱 환경이나 창에 액세스할 수 없습니다. 다른 응용 프로그램에 텍스트를 "입력"할 수 없습니다. 이 기능은 설계상 완전히 손상되었습니다.

3. **데스크톱 알림 없음(`notify-send`):** 위와 동일합니다. 컨테이너는 호스트의 데스크탑에 알림을 보낼 수 없습니다.

4. **파일 트리거 없음(`inotify`):** `inotify` 기반 파일 트리거는 예상대로 작동하지 않습니다. 호스트 시스템에서 단순히 `/tmp/sl5_record.trigger`를 터치할 수는 없습니다. 실행 중인 컨테이너 *내부*에 파일을 생성하려면 별도의 명령을 사용해야 합니다.
    ```bash
    docker exec stt-container touch /tmp/sl5_record.trigger
    ```

### 결론: "멋지지만" 근본적으로 호환되지 않음

이 Dockerfile을 생성하면 애플리케이션의 **핵심 로직**을 패키징할 수 있음이 입증됩니다. 그러나 이는 직접적인 하드웨어(마이크) 및 데스크톱(입력, 알림) 상호 작용에 의존하는 애플리케이션의 현재 설계가 **기본적으로 컨테이너화와 호환되지 않음**을 입증하기도 합니다.

Docker에서 이것이 실제로 작동하도록 하려면 애플리케이션을 다시 설계해야 합니다.
* 로컬 마이크를 듣는 대신 네트워크(예: 웹 API를 통해)를 통해 오디오 스트림을 수락해야 합니다.
* `xdotool`을 사용하여 텍스트를 입력하는 대신 동일한 웹 API를 통해 복사된 텍스트를 반환해야 합니다.
