# 动机：为什么“磁盘获胜”？

## Aura 奶奶模式中的问题

在 [Aura Oma Mode](../../../GettingStarted.i18n/GettingStarted-zh-CNlang.md)（见第 67 行）中，Aura 很大程度上自主运行：
用户说出命令，Aura 自行写入文件 —
配置、脚本、日志条目、生成的文本。

下面的场景不断发生：

1. 用户在编辑器中打开一个文件（例如规则文件或脚本）。
2. 他们忘记了编辑器仍然处于活动状态并说出 Aura 命令。
3. Aura 更改磁盘上的文件。
4. 编辑器检测到外部更改 - 并**提出**。

此提示在 Oma 模式中是一个**精彩**：
- 用户可能坐在沙发上，使用语音输入，
并且无法看到或到达该对话框。
- 或者他们不小心按下了编辑器中的某个键，缓冲区现在是
“修改”，并且每个外部更改块都带有一个
“重新加载？/保持本地化？”对话。
- 结果：Aura 继续工作，但编辑器显示陈旧的版本。
用户认为他们正在查看当前文件，但基于编辑
在一个旧的国家——混乱是必然的。

## 我们需要什么

**始终优先考虑磁盘的编辑器行为**。
当 Aura（或任何其他工具）更改文件时，编辑者必须
立即并**没有任何提示**显示新内容。
编辑器中未保存的输入可能会被默默丢弃 - 因为在
Oma模式，Aura是真理的来源，而不是人类的键盘输入。

## 为什么标准编辑器会失败

几乎所有常见的编辑器（Kate、VS Code、Sublime Text、Notepad++、
Emacs、Vim、CudaText 开箱即用）都有保护机制：
一旦缓冲区包含未保存的更改，他们**总是**询问
当外部发生变化时。这是正常情况下的功能
开发人员的工作——但 Aura Oma 模式的一个错误。

这个插件正好弥补了 CudaText 的这一差距。

## 目标受众

- Aura Oma 模式的用户在编辑器中并行查看文件。
- 进程写入文件和编辑器的自动化场景
仅作为现场观众。
- 任何人都希望“磁盘总是获胜”。
