# 動機: なぜ「ディスクが勝つ」のか?

## Aura おばあちゃんモードの問題

[Aura Oma Mode](../../../GettingStarted.i18n/GettingStarted-jalang.md) (行 67 を参照) では、Aura はほぼ自律的に動作します。
ユーザーがコマンドを話すと、Aura が独自にファイルに書き込みます。
構成、スクリプト、ログエントリ、生成されたテキスト。

次のシナリオが常に発生します。

1. ユーザーがエディターでファイルを開いている (ルール ファイルやスクリプトなど)。
2. 彼らはエディタがまだアクティブであることを忘れて、Aura コマンドを話します。
3. Aura はディスク上のファイルを変更します。
4. エディターは外部の変更を検出し、**質問します**。

このプロンプトは、Oma モードの **注目の的**です。
- ユーザーはソファに座って音声入力を使用している可能性があります。
ダイアログが表示されず、ダイアログに到達することもできません。
- または、エディターで誤ってキーを押した場合、バッファーは
「変更済み」であり、外部からの変更はすべてブロックされます。
「リロードしますか? / ローカルに保ちますか?」ダイアログ。
- 結果: Aura は動作し続けますが、エディターには古いバージョンが表示されます。
ユーザーは現在のファイルを見ていると思っていますが、編集は
古い状態では、カオスが保証されます。

## 必要なもの

**常にディスクを優先する**エディターの動作。
Aura (またはその他のツール) がファイルを変更するとき、編集者は次のことを行う必要があります。
すぐに、**プロンプトなしで** 新しいコンテンツを表示します。
エディターで保存されていない入力は、サイレントに破棄される可能性があります。
Oma モードでは、人間のキーボード入力ではなく、オーラが真実の源です。

## 標準エディターが失敗する理由

ほぼすべての一般的なエディタ (Kate、VS Code、Sublime Text、Notepad++、
Emacs、Vim、CudaText にはすぐに使用できる保護メカニズムがあります。
バッファに保存されていない変更が含まれるとすぐに、**常に** 質問されます。
外部の変化が起こったとき。これは通常の機能です
開発者の仕事ですが、Aura Oma モードのバグです。

このプラグインは、CudaText のまさにそのギャップを埋めます。

## 対象読者

- エディターでファイルを並行して表示する Aura Oma モードのユーザー。
- プロセスがファイルとエディタを書き込む自動化シナリオ
ライブビューアとしてのみ機能します。
- 「ディスクが常に勝つ」というのは、誰にとっても望ましい動作です。
